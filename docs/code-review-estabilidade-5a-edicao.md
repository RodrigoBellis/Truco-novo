O roteiro completo pelo navegador usa os controles reais contra o backend real em modo ensaio: 20 partidas de grupos embaralhadas, duas repescagens, duas quartas, duas semifinais e uma final. O campeão surge automaticamente; o histórico das outras quatro edições é conferido. Também cobre correções aceitas/recusadas, parceiros e adversários simultâneos, cadeado e permissões em cada fase, troca de jogadores, logout, refresh e conexão perdida antes e depois da gravação. Depois de perder uma resposta de resultado salvo, a tela lê o placar sem reenviá-lo.

A migração `202610090002_transactional_progression.sql` está **preparada e não aplicada**, assim como a migração de unicidade desta rodada. O backend local recusa gravações reais se a revisão transacional estiver ausente. Isso evita executar uma versão com garantias incompletas contra um banco não migrado.

Validação final: 116/116 testes do backend passaram; 10/10 cenários do ensaio completo passaram em desktop e celular (27 partidas iniciais em cada dispositivo, 11 correções no desktop e cinco no celular). A suíte de UI afetada passou com 50 testes; seus seis cenários exclusivos de ensaio foram ignorados nessa configuração e executados na configuração dedicada. Os testes específicos de placar salvo/final pendente passaram em quatro execuções. O script PostgreSQL local passou. Typecheck, lint e build passaram. Nenhum skip foi contado como teste aprovado.

Para executar os testes SQL locais: `node backend/scripts/test-knockout-postgres.mjs`. Ele só usa `127.0.0.1:55439`, não lê `.env`, não instala PostgreSQL e encerra seu próprio cluster. O schema é mínimo: não contém uma cópia das políticas RLS, gatilhos de auditoria ou configuração Auth do projeto compartilhado.

Antes de considerar o campeonato pronto, ainda é necessário conferir o review original e validar em um Supabase de homologação dedicado: projeto correto e histórico de migrações, aplicação das duas migrações locais necessárias, tipos regenerados, contas individuais reais, permissões/RLS/grants, gatilhos existentes, duas instâncias de backend, concorrência de cadeado/perfis/participações/edição, recuperação após reinício e simulação completa das 27 partidas. Deve-se conferir ainda que novas partidas não aceitam resultados enquanto a reconciliação anterior está pendente.

**Os testes em memória e o PostgreSQL local com schema mínimo não provam a segurança do banco real. Não foi liberado o campeonato para produção.** Depois da homologação e de uma autorização separada para implantação, a operação normal será abrir o cadeado; os empates absolutos continuam exigindo a decisão do administrador conforme as regras já aprovadas.
